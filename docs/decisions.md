# TinyCorp — Decisions

Numbered as they were made. Each records the alternatives so future changes are deliberate.

| # | Decision | Alternatives rejected | Why |
|---|---|---|---|
| 1 | Real orchestrator: a workspace maps to N real git repos and ships real code. | Company simulation with no code output. | The office is the hook; the loop is the retention. |
| 2 | Roles are data (persona + capabilities + repo filter), catalog provided, any composition valid. | Fixed PM/PO/HR/Dev roles; collapsing to one Manager. | A solo PM-who-codes and a full team must both work. |
| 3 | Every employee is a CLI session on the user's subscription. | Direct API calls for non-coders. | API cost; provider switching and repo access come free with CLI. |
| 4 | Agents touch the company only through an app-owned MCP server, plus injected instructions and skills. | Files as the bus; scraping PTY output. | One surface shared by all providers; exact state knowledge drives the office. |
| 5 | Long-lived sessions; app pushes prompts on idle, queues into an inbox while busy. | Ephemeral `-p` runs; agents polling. | Visible terminal, retained context, interruptible. **Validated by [spike v0](spikes/v0-loop.md)**: SessionStart = ready, Stop = idle, push = text + 250 ms + `\r`. |
| 6 | Three autonomy levels; Managed default gates merges and hires. | Everything free; everything gated. | Boss keeps money and main-branch decisions by default. |
| 7 | Own local board in SQLite is the source of truth; one-way sync out later. | Linear/GitHub as the board. | Agents hammer the board; must be local, fast, offline, and ours to shape. |
| 8 | Worktree per ticket, PR per repo, linked to one ticket. | Worktree per employee; shared checkout. | Parallel engineers on one repo must not collide; unfinished tickets must not block. |
| 9 | Target → Epic → Ticket → Subtask; subtasks are a checklist on one branch. | Subtasks as separate worktrees. | Worktree boundary = assignee boundary. Promote when another person or repo is needed. |
| 10 | Electron + TypeScript, own codebase, MIT pieces lifted from Pixel Agents and Orca. | Tauri; forking Orca. | Riskiest half (PTY, MCP, git) stays in the language we know; Orca's model is tabs, not teams. |
| 11 | Office shows seven real states plus the boss desk; feelings are chat text only. | Free-form emotion animations. | Every animation must be backed by a true system state. |
| 12 | Wake rules: DM, @mention, ticket reference, epic-channel membership; `#general` never wakes. | Every channel message wakes every member. | Token bill; idle agents cost nothing. |
| 13 | Free-chat intake routed by capabilities (`intake`, `plan`, `code`, `review`, `hire`). | Structured target form; user picks recipient. | Feels like a company; structure is the agent's job. |
| 14 | Claude Code only in v1, adapter seam for Codex and OpenCode. | Three adapters in v1. | Don't build idle detection three times before the loop is proven. |
| 15 | Cold restore via `--session-id` (app-chosen) + `--resume`, primed fallback, memory file per employee. PTY daemon deferred. | Daemon in v1; no restore. | Orca's daemon is a large lifecycle subsystem; v1 can pay a few seconds on launch. **Validated by [spike v0](spikes/v0-loop.md)**: resume found the pre-assigned id and the agent remembered its ticket. |
| 16 | Agent review when a `review` holder exists, then the merge gate. | Human-only review; auto-merge. | First place the company pays off in quality; still respects decision 6. |
| 17 | Hire = catalog role + gated chat request; `team_load` tool supplies numbers. | Hardcoded hiring triggers. | Hirer reasons from data; triggers stay in instructions. |
| 18 | Concurrency cap default 5, parked employees beyond it, one visible budget-exhausted state. | No cap; silent stalls. | Subscription limits are real; the company must react visibly. |
| 19 | PixiJS office; Pixel Agents layout and pathfinding ported as pure TS. | Port Canvas 2D renderer; Phaser. | Camera, zoom, filters, TS-native, no engine fighting React. |
| 20 | Kanban with WIP limits in v1; sprints on the roadmap as a gated switch. | Sprints in v1. | WIP limits already feed hiring; sprints are a lot of surface. |
| 21 | Notifications in v1. Codename `tinycorp`. Docs in repo. | — | User decision. |
| 22 | Spawn employees with all inherited `CLAUDE*` env vars stripped, and inject MCP via `--mcp-config … --strict-mcp-config`, not `.mcp.json`. | Inherit env; project `.mcp.json`. | Spike v0: inherited child-session marker disables transcripts; `.mcp.json` needs an approval prompt, `--mcp-config` does not. |
| 23 | SQLite through Node's built-in `node:sqlite` (Electron 44 ships Node 24), one `company.sqlite` per Company folder, schema versioned by named migrations (see 24). Recent Companies live in a JSON file in Electron's `userData`, outside the engine's domain state. | `better-sqlite3`. | No native module to rebuild for Electron's ABI, and the same code runs in Vitest on plain Node. |
| 24 | Migrations are `{ name, sql }` applied by name and recorded in a `schema_migration` table; databases that only carry the old positional `user_version` are adopted once. | Positional list index. | Two parallel branches appending at the same index left a database made on one branch permanently missing the other's tables (found landing T04). |
| 25 | An Employee's Session stays in the Company folder across tickets; on claim it is told its worktree paths in the ticket prompt instead of being restarted in a new cwd. | Restart the Session per ticket with cwd = worktree. | A long-lived session cannot change cwd; restarting would lose context every ticket (T12). |
| 26 | Firing is a soft delete: the Employee row keeps `fired_at`, the desk is freed, the Session stopped, open tickets unassigned; the memory file at `<company>/memory/<employeeId>.md` survives and rehiring reuses the same id. `fire_request` is gated like `hire_request`. | Hard delete. | "Fire keeps the memory" and rehire were both requirements (T14, T15, T20). |
| 27 | An unaddressed boss top-level message in any named channel except `#general` wakes the intake holder (wake kind `intake`); `#general` stays silent even for the boss. The intake holder may decide it is not a goal. | Route `#general` messages to intake as an exception to decision 12. | Keeps idle agents free; the explicit path (DM or @mention) already exists (T10). |
| 28 | An Employee's move of a ticket to Review goes through the `open_pr` autonomy gate (Managed: approval, then PRs open); the boss's own move opens PRs directly. Review rounds go to a `review` holder other than the assignee, else the boss; `review_submit` is read-only and approve passes the merge gate with CI state from `gh`. | Open PRs unconditionally on Review. | Opening a PR is an outward action; the gate table already named it (T12, T13). |
| 29 | When spawning a Session, every inherited `CLAUDE*` variable is stripped except `CLAUDE_CODE_OAUTH_TOKEN`, so a CI runner can log in with a `claude setup-token` credential and never an API key. The real-Claude test (`pnpm test:claude`) is separate from `pnpm test` and runs on main and on demand only. | Strip everything; run the real test on every push. | Decision 22 was too broad for CI (T19); the real test costs subscription usage and about 75 s. |
| 30 | `#general` wakes every Employee (reopens 12/27): messages arriving while an Employee is busy coalesce into one inbox item, and the wake prompt says no reply is needed unless it concerns them. The office task bar DMs the intake holder. | Keep `#general` silent. | The boss wants team-wide messages (an HR welcome) seen at once; coalescing and the no-reply prompt bound the cost. |
| 31 | No per-Employee autonomy level and no per-Employee money cap; the hire flow gains a model selector (`Employee.model`, passed to the adapter). Provider switching stays out of scope in v1 and its controls render inert as designed. | Per-Employee autonomy and $ caps as the mockup showed. | Decisions 3, 6, 14 and 18 hold; a model per Employee is real and cheap. |
| 32 | Tickets stay multi-repo; New Ticket picks repos with a multi-select chip row. | One repo per ticket. | Decisions 8 and 9. |
| 33 | Ticket ids carry a Company key: `TC-142`; `#142` remains a short form in chat. | Keep plain `#12`. | The design's ids read better across Companies; the reference parser accepts both. |
| 34 | Editing a role template propagates persona, capabilities and repo filter to every Employee on it that has not overridden them. | Copy at hire only. | "Roles are data" as the Employees page promises. |
| 35 | Out-of-budget and parked Employees sit in the coffee area. | Empty chair. | product.md and the design agree; the code chose otherwise. |
| 36 | Build Office regions (Region entity, Employees per region, per-region desks, sidebar counts and at-work dots) and an Activity event log (append-only event table written by the engine, Activity view). Repos gain `Scan a folder`; cloning from GitHub or a remote URL stays inert. | Defer regions and Activity; all repo sources now. | Regions and Activity are core to the office metaphor; cloning is network and auth surface for little gain. |
| 37 | The composer gets attachments (files stored in the Company folder, readable by Employees through MCP) and slash commands for existing actions. | Inert buttons. | User decision. |
| 38 | `Pause all` stops every Session (they resume on next start); the hire proposal is editable before approval and `team_load` gains per-role WIP and average time in Review with a max-headcount setting feeding the Autonomous gate; Company settings holds boss name and initials, Company rename, cap, autonomy and notifications; presence is a static label. The design's `Start work immediately` is hidden under Supervised and the Autonomous card reads "Asks only on red CI, limits and hires". | Pause as inbox freeze; minimal hiring; presence feature. | User decisions; wording fixed in the design. |
| 39 | Onboarding: after Create Company a five-step wizard (Company, Team preset, Your team, Repositories, First ticket) runs once, every step skippable. Presets (Solo builder, Product squad default, Full studio, Start empty) are shipped data. No money anywhere (decisions 3, 18, 31) and no ticket estimate before creation. Finish hires the roster, attaches the connected repos, starts Sessions up to the cap and DMs the goal to the intake holder, who welcomes the team in `#general` and breaks the goal into tickets. | Prices per seat and a monthly estimate; a model-call estimate; hire without starting; editable, re-runnable presets. | Keeps the cost model honest, avoids a model call in a form, and gets the boss to a working office in one flow. |
| 40 | A repo's stack is no longer a gate. Each repo carries a free-text brief ("About this repo") written into every Employee's instructions; install, build, test and lint become optional Checks, filled by detection, by the boss, or by the Employee who scaffolds the project through an MCP tool. A repo without Checks can be claimed; instructions say so, and Checks run before every PR once they exist. "Stack required" becomes a soft "No checks yet" hint. Reverses the mandatory stack in `product.md` and spec story 3. | Keep the mandatory stack; a stack wizard for new repos. | A freshly initialised repo has nothing to detect, and choosing its stack is the first ticket's work, so the gate blocked exactly the from-scratch flow (T61). |
| 41 | One voice: a boss message has one answerer. The answerer is the boss's "Who answers you" choice in Company settings, else the first Employee (hire order) holding `intake`, else the first holding `plan`, else the first hired; a parked, paused, stopped or out-of-budget answerer passes to the next in the chain, which says so; when nobody is available the message waits and the chat says it is waiting for capacity; with no Employees the message is kept and becomes the first hire's first item. Wakes: an unaddressed boss message in `#general` or any named channel wakes only the answerer (everyone else gets it unread, no wake); `@name` wakes only the named, not the answerer; `@channel` wakes everyone; a ticket reference with no mention goes to the assignee, else the answerer; a reply in a thread wakes the author of the message being answered (the previous non-author message, else the root author) plus mentions, never every participant; DMs only their recipient. Threads keep their answerer when the setting changes; if the answerer is fired, the next in the chain inherits open threads with their history. Instructions: do not repeat to the boss what a colleague said, do not post in `#general` unless you are the answerer or were named, corrections go as one reply in the same thread. Onboarding Finish and the hiring warning use the same chain. Reopens 12, 27 and 30; adjusts T60. | Everyone wakes on `#general` (decision 30); only a PM answers. | Decision 30 produced two answers to every boss message and agents apologising for crossed replies; a PM-only rule leaves Companies with custom rosters (only a Tech Lead, two PMs, capability-less roles) with nobody or everybody answering. |
| 42 | Approvals read as the design: the requester writes one human sentence and the facts live on a card with the `Waiting on you` badge. PR approvals use the designed PR card (repo, number, Mergeable, branch and diff line, checks); every other kind (open a PR, merge without a remote, hire, fire, limits) gets a generic approval card with the subject, the reason and the same Approve / Send back actions inline and in the thread panel. Native notifications drop the Company subtitle and carry the requester's initials where the platform allows. | Keep the raw `@boss Approval needed: may I …? Reason: …` template. | The audit flagged it (rows 107–110) and the boss found approvals hard to read. |
| 43 | The Chat sidebar gets an Inbox at the top: everything addressed to the boss (mentions, replies in threads the boss is in, pending approvals, DMs, "waiting for capacity" notices), newest first, unread first, with a count; clicking a row opens the channel with the thread panel on that message and marks it read; Mark all read. It is the boss's inbox, distinct from the Activity event log. | Only per-channel unread counts. | Slack-style: one place to see what needs you and jump to the thread. |
| 44 | Every merge an Employee performs, including a local merge in a repo without a remote, goes through the `merge` approval gate in the app's code flow; instructions forbid merging with git directly, and a chat message saying "I approve" is not an approval. | Trust instructions only. | An Employee merged a ticket from a DM "i approve" before the formal approval was decided. |
| 45 | Company data never enters a repo: initialising or attaching a repo writes a `.gitignore` entry for `company.sqlite*`, `memory/`, `worktrees/` and `attachments/` when the repo folder is or contains the Company folder, and refuses to commit them. The Launcher warns when a Company folder is under a temporary directory (`/tmp`, `/private/tmp`, `/var/folders`) and offers to move it. | Leave it to the boss. | The boss's company.sqlite was committed into a repo, and a real Company lived in a temporary folder. |
| 46 | Office movement follows a live chat exchange, and every sprite says why it moved. Two or more Employees posting in one channel or thread within two minutes meet in the glass room and stay for the exchange plus a short tail; one posting alone never leaves their desk. A DM or an `@Name` is a visit to that desk, a DM or `@boss` and a pending approval are a trip to the boss desk. Coffee means parked, out of budget or blocked; a desk collision takes a free desk first. No trip is shorter than 20 s and no Employee starts more than one a minute. A label under each sprite names the reason and a Legend on the canvas explains the states. Refines 35. | Talking for a flat 10 s after any post, alone, and coffee for desk collisions. | The boss: "agents movements doesn't make sense, it gets up and walks to a room alone, and then comes back to chair" (T74). |
| 47 | The boss is one person, not a field on each Company: name, handle, initials, character and status live in one profile in `userData` (`boss-profile.json`, beside `recent-companies.json`), and every Company reads it. The per-Company `boss_name` / `boss_initials` columns stay only as the migration source — the first Company opened without a stored profile seeds it — and Company settings' boss fields now write to the profile. Your profile is the page that edits it; the chosen character replaces the initials tile wherever the boss appears, with the initials as the fallback until the sheet decodes. A status (Available / Focused / Away, with an optional expiry) is recorded and shown but changes no routing yet. `Play a sound` is the boss's own setting and drives the native notification's `silent` flag; `Show notifications` stays the Company's (decision 38). | Keep the boss per Company. | One subscription, one person: two Companies showing different bosses was a bug the design never intended (T79). |
| 47 | One voice is narrowed to the boss's own unaddressed messages (refines 41). `@channel` is the boss asking everyone and every Employee answers for itself, once and briefly; a colleague posting in `#general`, a new hire saying hello among them, is ordinary conversation the team joins in; whoever is named answers while the answerer stays out. The wake rules do not change: an unaddressed boss message still wakes only the answerer, and everything else in `#general` arrives unread. | Keep decision 41's etiquette, which also told Employees never to post in `#general` unless they were the answerer or were named. | The boss asked everyone something and only one Employee replied, and nobody welcomed a new hire: the rule meant to stop two answers to the boss was silencing the team everywhere. |
| 48 | An Employee's instructions travel on its own process, on `--append-system-prompt`, and nothing Employee-specific is written into the Company folder; a `CLAUDE.md` an earlier build generated there is deleted at spawn. | Keep writing `<company folder>/CLAUDE.md`; or give each Employee its own working directory under the Company folder, each with its own `CLAUDE.md`. | Every Session runs with the Company folder as its cwd, so one file there was rewritten by whoever started last and read by all of them: Hera and Orion both introduced themselves as "Arlo, PO" (T96). | 54 | TinyCorp ships as a macOS app: `pnpm package` builds `TinyCorp.app` and a DMG with electron-builder, arm64 only, unsigned and un-notarised (ad-hoc from Electron's own binary; the boss opens it the first time with right-click → Open). | 55 | A Provider is an entry in `src/shared/domain/providers.ts`, an adapter that passes the conformance suite in `src/main/providers/provider-conformance.ts`, and one line in `src/main/providers/provider-registry.ts`. | 56 | Adding a Provider is a pull request a stranger can send: `docs/providers.md` is the guide for someone who has never opened the repo, `CONTRIBUTING.md` says what such a PR must and must not include, and `pnpm provider:new <id>` copies the template in `src/main/providers/example/`, renames it and writes the catalogue entry, the registry line and the docs row. Refines 55. | A guide alone, with the seam as T116 left it. | "Easy for someone who is not us" is not a feeling: the first move had to be a command rather than a copy-paste, the first test run had to say what was missing in words rather than diff two objects, and the promise that one entry is the whole edit had to be a test rather than a sentence. |
| 57 | An Employee gets the MCP servers the boss gives it, and no others. The Company holds a catalogue of outside MCP servers (name, transport, URL or command, arguments, environment), typed in once in Company settings → Integrations; the grant is a job field beside persona, capabilities and repo filter, so a role hands its servers to everyone hired into it and an Employee can override. `injectMcp` takes the granted servers as well as the Company's own and each Provider writes them the way its product reads them, with its strictest MCP flag still on; the conformance suite checks that a granted server reaches the process, that an ungranted one does not, and that no secret is in `argv`. A token lives in the macOS keychain under the Company and the server's id, written over `security -i`'s stdin, read once at spawn and never returned by anything; removing a server says how many Employees and roles hold it, then takes the grant off all of them. No MCP tool grants an MCP server, and no code path reads the boss's own Provider config to discover one. | Let a Session inherit the boss's own MCP config by dropping `--strict-mcp-config`; or let a `hire` holder propose servers along with the rest of a hire. | The flag is right — an Employee is not the boss — but there was no way to grant anything on purpose. Making the grant a job field means the existing follow-the-role machinery (decision 34) works unchanged, and keeping it off the MCP surface means no Employee can widen its own hands, the way deleting a channel and setting a topic are the boss's (T112, T44). |
| 58 | An Employee gets the skills the boss gives it. A skill is a name and a folder on this Mac — a review checklist, a deploy runbook, the way this team hands a design off — picked with the folder picker in Company settings → Integrations; the catalogue stores the path and never copies the folder in, and TinyCorp never parses, validates or runs anything in it. The adapter puts each granted folder where its product reads it — Claude Code's `.claude/skills/` in the Employee's worktree — as a symlink, git-excluded (decision 45), and takes it away when the grant goes; `installSkills` is the one **optional** part of the Provider contract, and a Provider that reads no skill folders says so in its catalogue entry and on the Employee's drawer (`<Provider> — no skills`) rather than the app pretending the grant did something; every Provider in the catalogue reads one since T253, each confirmed against its installed CLI rather than guessed. A folder that has moved says so on the row, on the chip and in the instructions, and fails no spawn. No Employee grants a skill, and a hire proposal carries none. | Copy the folder into the Company, so a grant is a snapshot; or let the app read a skill and act on it. | A symlink means the boss edits the folder once and every Employee holding it sees the edit, and nothing duplicates; a copy is stale the moment it is made. And a skill is instructions, so where the folder came from is the same trust as a repo the Company works in — which is the boss's call to make, never an Employee's. |
| 59 | A forge — where a repo's pull requests live — is an entry in `src/shared/forges/index.ts`, an adapter that passes the conformance suite in `src/main/forges/forge-conformance.ts`, and one line in `src/main/forges/forge-registry.ts`; `gh` is the first client of that suite rather than the baseline. Which forge a repo is on is **per repo**, read from its `origin` and shown on the repo card, so one Company can hold repos on several at once. Authentication is the CLI's: TinyCorp holds no forge token, reads none and passes none, and a check in the suite watches every command for one. A repo whose forge has no adapter — an unlisted product, or a self-hosted instance on a host nobody can list — attaches, works for everything local, and says in words, on the card, on the ticket, in `#prs` and in the Employee's own instructions, that the pull request is the boss's to open. No screen names a forge, and a test asserts it. The same shape as decisions 55 and 56, for the other seam. | Keep `gh` inline in `git-service.ts` and add a second forge when someone asks; or store the forge as a field the boss picks when attaching a repo. | `git-service.ts` shelled out to `gh` for every dealing with a forge, so GitHub was not a choice the app had made once but a wire through the only path a PR could take — and a boss with ten repos at an employer on GitLab could not use the app at all. The forge is a fact about the remote, not a preference, so asking for it would be asking the boss to repeat what git already knows, and getting it wrong would open a PR in the wrong place. |
| 60 | The boss commits from the app; TinyCorp never does it on its own. The Files view gets a Changes tab beside the tree: one group per `FilePlace` — an Employee's worktree for a ticket, and the Company's own repos last — each with its own `git status`, its own files, and its own commit box, because a ticket gets a worktree per repo and there is no *the* working tree to commit. Stage, unstage, commit and push are the boss's clicks and nothing else's; a group whose Employee has a Session running carries the warning the file editor already gives for the same hazard; and discard — the one action that loses uncommitted work — is confirmed, names its files, and takes a restore point first where the place is a ticket worktree (T118). The status is cached per place and invalidated by the events the app already has — a Session's hook, a worktree created, a ticket moved, the boss's own save — never by a timer, and nothing walks a repo the Company does not already list. Reads decision 45. | A flat list of dirty files with one commit box, as VS Code has; a Changes tab that only shows; committing for the boss when a Session goes idle. | Decision 45 says the app writes into a worktree but never commits: that means **TinyCorp** does not commit behind your back, not that the boss may not commit from their own window — the Employee's Session is what commits today, and a click of the boss's is a human action either way. A flat list would be a lie about how this app works, because every change here is somebody's, for something, and the grouping is not invented: it *is* the place (T160). |
